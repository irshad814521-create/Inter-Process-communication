    Key takeaways from the simulation

    1. Safety vs. speed. Pipes and message queues let the kernel handle synchronization, which is safer but slower. Shared memory skips the kernel copy, but the race-condition demo (lock off) shows the price: a corrupted value (??).
    2. Structure of data. A pipe is an unstructured stream. A message queue keeps boundaries and types, so B can ask for only type 2.
    3. Scope. Only sockets work across machines. They pay for the handshake (SYN, SYN-ACK, ACK) and teardown.
    4. Information carried. Signals carry almost no data. SIGINT, SIGTERM and SIGUSR1 can be handled, while SIGKILL always terminates.
    5. Blocking behavior. A full pipe blocks the writer, an empty pipe blocks the reader, and a queue with no matching message makes the receiver wait. Shared memory never blocks, so it needs manual coordination.

    Quick decision guide

    • Maximum throughput between local processes? Shared memory, with locks.
    • Simple one-way data flow, like a shell pipeline? Pipe.
    • Typed, well-separated messages? Message queue.
    • Two-way communication, or different machines? Socket.
    • Just need to tell a process to stop or reload? Signal.
